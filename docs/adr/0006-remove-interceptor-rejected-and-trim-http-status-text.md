# 移除拦截器 rejected 恢复语义并精简 HTTP 状态码表

Status: accepted

## 背景

对 `createFetch` 的"是否过度封装"审查结论：定位为请求框架（错误归一化、拦截器、去重、取消四件套均为核心能力，ADR 0001-0005 的复杂度有据），但存在两处偶然复杂性：

1. **拦截器 `rejected` 恢复语义是反直觉的自创契约**："返回 truthy 恢复、falsy 错误成立"与 axios 的"rejected 透传错误"心智不同；测试套件虽覆盖 8 个用例，但无使用方使用证据；它与 `fulfilled` 返回值校验叠加，产生两套守卫（恢复值 + 返回值），并牵动 ADR 0002 §3、0003 §4、0004 §3 三条条款。
2. **HTTP_STATUS_TEXT 51 条映射表超出"msg 恒有值"的需求**：调用方实际消费 `ok`/`code`/`data`（业务 code 在 data envelope 中），`HTTP ${code}` 回退已满足恒有值；测试仅依赖 200/204/401/500 四条描述，其余条目无行为收益。

同时确认维持不变的事实：去重 × 取消的广播语义（ADR 0003 §3 / 0005 §4）被实际使用——去重请求会取消，保留；请求框架定位成立。

## 决策

### 1. 移除拦截器 `rejected` 恢复语义

`Interceptor` 仅保留 `fulfilled`；`use(fulfilled)` 不再接受第二个参数；请求/响应拦截器链中 `fulfilled` 抛错一律由错误归一化收口（`CancelError` → `-1`，其余 → `-4`，响应链保留响应现场）。`fulfilled` 返回值运行时校验保留（请求侧校验配置形状、响应侧校验结果形状，见 ADR 0005 §1 / ADR 0002 §5）。

取代并失效的既有条款：ADR 0002 §3（rejected 签名）、ADR 0003 §4（rejected 恢复值校验）、ADR 0004 §3（请求拦截器恢复值校验收紧）。

### 2. 精简 HTTP_STATUS_TEXT

51 条裁剪为 34 条常用码：1xx `100, 101`；2xx `200, 201, 202, 204, 206`；3xx `300, 301, 302, 304, 307, 308`；4xx `400, 401, 402, 403, 404, 405, 406, 408, 409, 410, 413, 415, 417, 422, 429`；5xx `500, 501, 502, 503, 504, 505`。未收录码回退 `HTTP ${code}`。msg 行为不变量（恒有值、不透传 errMsg）不变。

### 3. 维持不变

- 定位：请求框架，错误归一化/拦截器/去重/取消四件套为核心。
- 去重 × 取消广播语义（ADR 0003 §3 / 0005 §4）：去重请求会取消，共享执行（传输层）不中断、同 key 调用者（含等待者）统一 `-1`。
- `fulfilled` 返回值运行时校验（ADR 0005 §1 / ADR 0002 §5）。

> 注：上述"去重请求会取消，共享执行（传输层）不中断"已被 ADR 0007 取代——abort 为整组取消，共享执行（传输层）随之中止。

## 后果

- 拦截器 API 面收敛：仅 `fulfilled`，抛错即归一化，无恢复分支；代码与测试量下降（删除 8 个 rejected 用例）。
- HTTP 表体积缩减约三分之一，未收录码行为不变。
- 与 axios 的心智差距收窄：拦截器 throw → 归一化结果（而非异常路径），契约更简单。
- 错误归一化契约（ADR 0001）不变：业务 envelope 校验仍在响应拦截器 `fulfilled` 中 throw 后归一化为 `-4`。

## 被驳回的替代方案

- **保留 rejected 仅文档化**：反直觉语义继续存在，无使用证据支撑其复杂度。
- **rejected 与 fulfilled 校验一并移除**：拦截器漏 `return config` 会回到静默产出畸形 URL 的问题，而校验成本极低，保留更优。
- **HTTP 表整体删除、恒用 `HTTP ${code}`**：丢失常用码的可读性，保留常用子集收益更高。
