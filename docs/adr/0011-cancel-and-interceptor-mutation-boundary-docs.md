# 取消与拦截器改写边界语义文档化

Status: accepted

## 背景

对 `createFetch` 的第五次审查（续）确认三处既定行为存在文档缺口，均不涉及实现改动：

1. **取消不打断拦截器代码执行**：`abort(key)` 在响应拦截器阶段触发时，拦截器函数本身仍会执行完毕（副作用发生），只是其结果被丢弃并归一化为 `-1`。这是 `createCancelable` 机制的固有属性（注册同步、执行微任务、取消仅拒绝 Promise），非缺陷但未文档化。
2. **未知 key 的 abort 静默 no-op**：`abort('不存在的key')` 无任何提示。与"key 唯一性告警"（ADR 0005 §3，防真实误伤）不同，此路径无副作用；且请求完成后对旧 key 的兜底取消是合法且高频的调用模式，告警只会成为噪音。
3. **拦截器改写边界未声明**：请求拦截器收到的 `fullRequestConfig` 中，`header` 为每次请求合并出的新对象（ADR 0003 §1），改写安全；但 `rawRequestConfig` 与 `data` 是调用方传入对象的原始引用，改写会泄漏到调用方对象。

## 决策

### 1. `abort` 文档化取消边界

`abort` 的 JSDoc 补充：取消只丢弃未落定的结果，不打断已进入的拦截器代码执行（其副作用仍会跑完）；未知 key 的 abort 为静默 no-op（请求完成后对旧 key 的兜底取消是合法用法）。

### 2. 拦截器改写边界文档化

`interceptors` 的 JSDoc 补充改写边界：`header` 为合并副本可安全改写；`rawRequestConfig` 与 `data` 为调用方原始引用，不应修改。

## 后果

- 取消语义的"不打断执行"边界有文档约束，调用方不会误以为 abort 可中断拦截器副作用。
- 静默 no-op 与告警场景的界线明确：no-op 无副作用故不告警，key 冲突有误伤故告警。
- 拦截器改写边界可预期，避免调用方无意中污染自己传入的对象。

## 被驳回的替代方案

- **响应拦截器期间 abort 强行中断（如引入可重入检查）**：需破坏 `cancelable` 的通用机制，收益不成比例。
- **未知 key 的 abort 加 warn**：stale abort 合法且高频，warn 成为噪音；与 key 冲突告警（有实际破坏）性质不同。
- **拦截器参数深拷贝（防改写泄漏）**：`rawRequestConfig` 的保留本意就是原始引用（ADR 0003 §1），深拷贝改变契约且增加成本。
