# 去重请求取消：abort 整组取消

Status: accepted

## 背景

对去重 × 取消交互的语义演进：

1. ADR 0003 §3 曾采用"每调用者外层 cancelable 包装 + 共享执行剥除 key"，实现"abort 只取消调用者自身、共享执行不中断"——复杂度最高，双轨取消（外层 + core 内）心智成本大；
2. 其后一度改为"去重与取消互斥（abort 对去重请求无效）"，丢弃了使用方"去重请求会取消"的诉求；
3. 最终收敛：去重请求的取消语义定为**整组取消**——共享执行透传用户 key，`abort(key)` 中止整组共享执行，执行者与所有等待者统一收到 `code: -1`。

## 决策

### 1. 去重路径透传用户 key

`request()` 去重分支不再剥除 key、也不做每调用者包装，直接 `asyncDedupe(dedupKey, () => core(fullRequestConfig))`。共享执行带着用户 key 运行，core 内的拦截器与传输层按 ADR 0004 §1 注册取消监听并绑定 `requestTask.abort()`。

### 2. abort(key) = 整组取消

`abort(key)` 中止整组共享执行：执行者与所有等待者统一收到 `code: -1`。任一调用者 abort，全体等待者同收中止结果（误伤语义，见后果）。请求拦截器改写 key 在去重路径同样生效（与 ADR 0004 §1 一致）。

### 3. 取代并失效的既有条款

- ADR 0007 的早期互斥草案（abort 对去重请求无效）；
- ADR 0003 §3（每调用者包装的广播取消 + 共享执行不中断）；
- ADR 0005 §4（key 剥除 → 改写不生效、不可取消）；
- ADR 0006 §3 维持不变的"去重请求会取消，共享执行（传输层）不中断"。

## 后果

- 代码最简：无每调用者包装、无 key 剥除的 spread。
- 误伤语义：去重组中任一调用者 `abort(key)`，全体等待者同收 `-1`（与"共享同一结果"模型一致——取消也是共享的）。
- 共享执行（传输层）会因 abort 而真正中止（`requestTask.abort()` 被调用）。
- CONTEXT.md 取消/去重/去重等待者词条同步为整组取消语义。

## 被驳回的替代方案

- **每调用者包装（ADR 0003 §3）**：复杂度最高，为"只取消自身"的精细语义买单。
- **互斥不可取消（ADR 0007 早期草案）**：丢弃"去重请求会取消"的诉求，与使用方意图相悖。
