# 响应拦截器链与取消/框架错误的边界语义

Status: accepted

## 背景

`createFetch` 的 core 流程中，响应拦截器链的输入并非全部失败结果：传输层失败（`-1` 平台中止 / `-2` 超时 / `-3` 未知，经 `complete` 回调 resolve）与 HTTP 错误的结果会进入响应拦截器链；而用户主动 `abort(key)`（含去重起跑前短路，见 ADR 0018）与框架错误（`uni.request` 同步抛错）走 `catch → normalizeError` 提前返回，跳过响应链；拦截器抛错处链条中断（`-4`）。同是 `code: -1`，传输层中止进链、用户取消不进链——这一不对称此前仅存在于代码中，未在任何文档中明示。

## 决策

维持现状，并将边界文档化：

1. **用户取消与框架错误的结果不进响应拦截器链**：取消是「丢弃」语义，不打断业务链、不触发业务拦截器副作用；框架错误同理（请求从未发出，无响应现场可供处理）。
2. **传输层失败与 HTTP 错误的结果进响应拦截器链**：拦截器是业务错误判定与统一处理的场所，超时/平台中止/未知错误与 HTTP 错误一样属于「请求已发出并落定」的结果，理应可见。
3. 边界写入 CONTEXT.md 词条「拦截器与失败结果的边界」。

## 后果

- 响应拦截器无法观测用户取消（需要全量失败观测时，调用方按 `code` 聚合，`-1` 时可用 `instanceof CancelError` 区分主动取消与传输层中止）。
- 传输层失败结果可被响应拦截器改写或抛错（如 `!ok` 时抛业务异常），此时 `-4` 收口并保留响应现场——拦截器对失败结果的处置能力保持完整。
- 新增 CONTEXT.md 词条说明，未来调整边界（如统一进链）属破坏性变更，需新 ADR。

## 被驳回的替代方案

- **全量失败结果（含用户取消）都进响应拦截器链**：统一日志/埋点更顺，但拦截器按 `!ok` 抛错时会把用户取消的 `-1` 再转成 `-4`，取消「不打扰」的直觉被破坏；且取消发生在任意时刻，拦截器链上不可重入的副作用（如弹窗）可能被取消触发。
- **失败结果一律不进响应拦截器链**：拦截器失去对超时/平台中止的处理能力，与「拦截器是业务错误判定场所」的核心用法冲突，破坏面大。
